The short version

Run these in PowerShell 7, from the repository's pet folder.

  1. Change a setting in matrix_rain_8032_noclock_v8.asm, and the same setting in matrix_rain_8032.c. See Change the settings.

  2. Assemble the .prg:

    acme -f cbm -o matrix_rain_8032_noclock_v8.prg matrix_rain_8032_noclock_v8.asm

  3. Build the C version and check that the two still match:

    .\build.ps1 -Test

  4. Watch it run. .\build.ps1 -Run opens the C version in VICE; for the assembly version, see Matrix Rain in VICE.

  5. Commit the sources and the rebuilt .prg files together.

The files

Everything for the PET is in the repository's pet folder, and this guide's commands run from there. build.ps1 finds its files wherever you run it from, so .\pet\build.ps1 from the repository folder works too.

SourceBuildsWithWhat it is
matrix_rain_8032_noclock_v8.asm matrix_rain_8032_noclock_v8.prg ACME The original, in 6502 assembly: 80 columns, 70 drops. The C version's test compares against this .prg.
matrix_rain_4032.asm matrix_rain_4032.prg ACME The 40-column version. It has no C version and no automated test.
matrix_rain_8032.c matrix_rain_8032_c.prg cc65, through build.ps1 The 8032 version in C. It draws the same screen, more slowly.

The .prg files are committed next to their sources, so anyone can run them without building anything. After a change, rebuild the .prg and commit it with the source.

In the tools folder, asm_harness.c, asm_blob.s and sim_asm.cfg run the 8032 .prg inside cc65's 6502 simulator for the test, and profile.ps1 shows where the C version's time goes.

Change the settings

Eight numbers shape the rain. In the assembly they are data bytes at the end of the file, under Configuration Variables:

matrix_rain_8032_noclock_v8.asm
GLITCH   !byte 64              ; trail glitch frequency (0=off, 255=constant)
TRAILMIN !byte 10              ; minimum trail length (rows)
TRAILMAX !byte 24              ; maximum trail length (rows)
REVERSE  !byte 64              ; reverse video chance (0=never, 255=always)
NEWCHAR  !byte 51              ; new char chance (lower=more flicker)
NUMDRIPS !byte 70              ; active columns (max 80, try 70 for gaps)
SPDSTART !byte 9               ; initial speed range (0 to N-1, lower=faster)
SPDRESET !byte 5               ; reset speed range (0 to N-1, lower=faster)

In matrix_rain_8032.c they are the #define lines at the top, with the same names.

Setting80324032What it controls
GLITCH6464How often a drop swaps a character in its trail for a new one: the chance out of 256, each frame. 0 turns it off.
TRAILMIN1014The shortest trail, in rows. Each drop picks a length when it starts.
TRAILMAX2424The longest trail, in rows.
REVERSE6464The chance out of 256 that a new head character is in reverse video.
NEWCHAR5151The chance out of 256 that a head changes to a new character on a given frame. Higher flickers more. (The comment in the source says lower; the code does the opposite.)
NUMDRIPS7040How many drops fall at once: at most 80 on the 8032 and 40 on the 4032. Fewer than the number of columns leaves gaps.
SPDSTART915Each drop's first speed is picked from 0 up to one less than this. A speed is the number of frames a drop waits between moves, so lower is faster.
SPDRESET58The same, for a drop starting again at the top. Lower than SPDSTART makes the rain speed up after the first wave.

Values that stall it

SPDSTART and SPDRESET must be at least 1, and TRAILMAX at least TRAILMIN. Otherwise the program keeps rerolling a speed or a trail length that can never fit, the screen clears, and nothing falls.

Change both 8032 files

build.ps1 -Test runs the assembly and the C version from the same starting point and fails unless they leave every byte of screen RAM the same. A setting changed in only one of the two files fails the test. That is on purpose: the test is what keeps the two versions identical.

Build the assembly

With ACME, from the pet folder:

acme -f cbm -o matrix_rain_8032_noclock_v8.prg matrix_rain_8032_noclock_v8.asm
acme -f cbm -o matrix_rain_4032.prg matrix_rain_4032.asm

-f cbm puts the load address, $0401, in the first two bytes of the file. A PET program file needs it, and LOAD uses it to place the program.

Or with C64Ass, told to read ACME's syntax (-A ACME) and write a PET program file (-F CBM):

C64Ass -A ACME -F CBM -O matrix_rain_8032_noclock_v8.prg matrix_rain_8032_noclock_v8.asm
C64Ass -A ACME -F CBM -O matrix_rain_4032.prg matrix_rain_4032.asm

C64Ass prints one warning, W1004_UNUSED_CONSTANT - Unused constant SCREEN_LO. It's harmless: the constant records where the screen starts, and no instruction uses it.

A quick way to check your tools before you change anything: with the settings as they are, both commands write files identical, byte for byte, to the committed ones.

The first line of the program is a line of BASIC, 10 SYS 1040, so RUN starts the machine code.

Build the C version

.\build.ps1
Output
Built matrix_rain_8032_c.prg (1,449 bytes)

.\build.ps1 -Run builds it and opens it in VICE on a PET 8032.

By hand, the same build is:

cl65 -t pet -Oi -Cl -o matrix_rain_8032_c.prg matrix_rain_8032.c
OptionWhat it does
-t petBuilds for the PET. cc65 adds the BASIC line that starts the program.
-OiOptimises, inlining more code. About 7% faster here than plain -O.
-ClGives local variables fixed addresses instead of places on cc65's slow software stack. Safe because nothing in the program calls itself.

Check your change

.\build.ps1 -Test

This takes a few seconds and needs no emulator. It builds the C version for cc65's 6502 simulator, runs it for 400 frames, and prints the screen as text: . for an empty cell, * for a character, # for a reverse-video one. Then it runs the committed 8032 .prg in the same simulator and compares the two. It finishes like this:

Output
Screen RAM: all 2,048 bytes match the assembly's after 400 frames
Frame cost: 31,372 cycles (1.88x the 16,667-cycle retrace budget, about 32 fps)
Assembly:   18,453 cycles, so the C version takes 1.70x as long
Screen RAM
Both versions left the same bytes on screen, including the 48 bytes of screen memory past the last visible row.
Frame cost
What one frame costs the C version, in 6502 cycles. At 1 MHz and 60 frames a second a frame has 16,667 cycles, so the C version draws about 32 frames a second.
Assembly
The same measurement for the assembly, timed on the same simulated clock.

Assemble first

The test reads the committed matrix_rain_8032_noclock_v8.prg, not the .asm. After changing the assembly, rebuild the .prg before running the test, or you'll be testing the old program.

To see which parts of the C version a frame's cycles go to, run ..\tools\profile.ps1.

The 4032 version has no automated test. Assemble it and watch it in VICE on a PET 4032.

Changing the code itself

Anything beyond the settings in the 8032 version also goes into both files, and the random number calls must stay in the same order. Both versions draw every random choice from one generator with the same starting seed. Each call moves the generator on, so one extra or missing call changes every choice after it and the two screens drift apart.

Moving code in the 8032 assembly also breaks the test's harness, tools\asm_harness.c. The harness can't run the program's main loop, because that waits for a screen refresh the simulator doesn't have. So it calls the setup code at $0415 and DRAW at $0464 directly. It checks the bytes at $0410 and at the main loop, $0457, first. If code before DRAW changes size, the test stops with:

Output
asm_harness: init and DRAW are not where this expects them.
The .prg has changed; update the PET_ addresses to match.

To find the new addresses, have the assembler write its labels to a file, with -l labels.txt for ACME or -L labels.txt for C64Ass. In C64Ass's file, the two you need look like this:

labels.txt, from C64Ass
MainLoop = $0457;
DRAW = $0464;

Put them into PET_MAINLOOP and PET_DRAW in the harness. Update the jsr DRAW bytes in mainloop_code too, since they hold DRAW's address.

If something goes wrong

cl65 not found at … Pass -Cc65 <path to cc65>.
cc65 isn't in the folder build.ps1 expects. Pass -Cc65 with the folder that holds bin\cl65.exe.
xpet not found at … Pass -Vice <path to VICE>.
The same for VICE: pass -Vice with the folder that holds bin\xpet.exe.
… cannot be loaded because running scripts is disabled on this system.
Windows is blocking PowerShell scripts. Allow your own scripts once with Set-ExecutionPolicy -Scope CurrentUser RemoteSigned. If you downloaded the repository as a zip, also run Get-ChildItem -Recurse *.ps1 | Unblock-File in its folder.
Screen RAM differs from the assembly's in … bytes after 400 frames.
The two versions drew different screens. Check that the settings match in both files and that you rebuilt the .prg after changing the assembly. The message gives the first address that differs and both values.
asm_harness: init and DRAW are not where this expects them.
Code in the assembly moved. See Changing the code itself.
The screen clears and nothing falls
A setting is out of range. See Values that stall it.

The build.ps1 and C64Ass commands above were run on Windows 11 on 18 September 2026, with cc65 2.19 and C64 Studio 8.3, and the output shown is from those runs. With the settings unchanged, every rebuilt .prg matched the committed one byte for byte. The ACME commands weren't run, because ACME isn't installed on that machine; C64Ass assembled the same sources in ACME's syntax.
