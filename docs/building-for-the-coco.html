The short version

Run these in PowerShell 7, from the repository's coco folder for the CoCo 1/2 version, or its coco3 folder for the CoCo 3. The commands are the same in both.

  1. Change a setting in the .asm file, and the same setting in the .c file beside it. See Change the settings.

  2. Build everything and test it:

    .\build.ps1 -Test

  3. Watch it run:

    .\build.ps1 -Run

  4. Commit the sources with the rebuilt .bin, .cas and .dsk files.

The files

The CoCo 1/2 files are in the repository's coco folder and the CoCo 3 files in coco3. Each folder has its own build.ps1, which finds its files wherever you run it from.

Each CoCo program has a reference model: a C copy of it, in the matching .c file, that runs in cc65's 6502 simulator instead of on a CoCo. The test runs the program and its reference model for 400 frames each and requires them to leave the same screen. The C copies descend from the PET's C version, which was itself checked byte for byte against the PET assembly, so this keeps every version drawing the same rain.

The three kinds of output:

.bin
Disk BASIC's machine-code file: the program's bytes, where they load, and where to start. XRoar runs one directly.
.cas
A cassette recording, as data. CLOADM reads it.
.dsk
A 35-track Disk BASIC floppy image. LOADM reads it.

LWTOOLS writes only the .bin. tools\coco_images.ps1 writes the tape and disk images from it, and tools\xroar.ps1 runs XRoar with no window for the tests. tools\test_coco_tools.ps1 tests those two, using the small program in tools\fixtures\fill.asm.

Building LWTOOLS on Windows

LWTOOLS comes as source code, with a Visual Studio solution in its win folder. You need Visual Studio with its C++ desktop tools.

  1. Download the LWTOOLS 4.25 source from lwtools.ca and unpack it. Windows' own tar can unpack a .tar.gz: tar -xzf lwtools-4.25.tar.gz.

  2. Build the release version, 32-bit, from a Developer PowerShell for Visual Studio, which has msbuild on its path:

    msbuild lwtools-4.25\win\lwtools.sln /p:Configuration=Release /p:Platform=Win32

    If it says the project's platform toolset isn't installed, add yours: /p:PlatformToolset=v145 for Visual Studio 2026, v143 for 2022.

  3. Copy lwtools-4.25\win\lwasm\Release\lwasm.exe into a folder of your choice, and give that folder to the scripts as -Lwtools.

One part fails: lwlink, the linker, stops on an unresolved strcasecmp. This project doesn't use it. To build it anyway, run $env:CL = '/Dstrcasecmp=_stricmp' before msbuild.

Change the settings

The settings sit in a Configuration block near the top of each .asm file, as equ lines, and as #define lines near the top of its .c file.

The CoCo 3 files have two blocks. The one under IFDEF COMPOSITE (#ifdef COMPOSITE in the C) is the 40-column build for a TV; the one under ELSE is the 80-column build for an RGB monitor.

matrix_rain_coco.asm
GLITCH   equ  64           ; trail glitch frequency (0=off, 255=constant)
TRAILMIN equ  6              ; minimum trail length (rows)
TRAILMAX equ  14             ; maximum trail length (rows)
REVERSE  equ  64             ; highlight chance (0=never, 255=always)
NEWCHAR  equ  51             ; new char chance (lower=more flicker)
NUMDRIPS equ  28             ; active drops (max 32)
SPDSTART equ  9              ; initial speed range (0 to N-1, lower=faster)
SPDRESET equ  5              ; reset speed range (0 to N-1, lower=faster)
GRAPHIC  equ  16             ; graphics block chance (0=never, 255=always)
BLOCKGLITCH equ 128          ; chance a green block changes each time the
                             ; sweep visits it, every 4 frames (0=never,
                             ; 255=always)
SettingCoCo 1/2CoCo 3 RGBCoCo 3 TVWhat it controls
GLITCH646464How often a drop swaps a character in its trail for a new one: the chance out of 256, each frame. 0 turns it off.
TRAILMIN61014The shortest trail, in rows. Each drop picks a length when it starts. At least 5 on the CoCo 3, which needs the rows for its fade.
TRAILMAX142323The longest trail, in rows.
REVERSE646464The chance out of 256 that a new head is highlighted: a dark letter on bright green.
NEWCHAR515151The chance out of 256 that a head changes to a new character on a given frame. Higher flickers more. (The comment in the source says lower; the code does the opposite.)
NUMDRIPS286540How many drops fall at once. At most 32 on the CoCo 1/2, and at most the number of columns on the CoCo 3.
SPDSTART9915Each drop's first speed is picked from 0 up to one less than this, at most 32. A speed is the number of frames a drop waits between moves, so lower is faster.
SPDRESET558The same, for a drop starting again at the top, also at most 32. Lower than SPDSTART makes the rain speed up after the first wave.
GRAPHIC161616The chance out of 256 that a new character is a green graphics block (CoCo 1/2) or an accented foreign letter (CoCo 3).
BLOCKGLITCH128255255The chance out of 256 that a block or foreign letter already in a trail changes when a sweep of the screen reaches it. The sweep covers the whole screen every 4 frames on the CoCo 1/2 and every 8 on the CoCo 3.

The limits in the table are enforced. Break one, and lwasm stops with a message such as SPDSTART must be 32 or less, and the C file stops with a matching #error.

Values that stall it

Two limits aren't enforced. SPDSTART and SPDRESET must be at least 1, and TRAILMAX at least TRAILMIN. Otherwise the program keeps rerolling a speed or a trail length that can never fit, and nothing falls.

Change the .asm and the .c together

The test fails until the program and its reference model agree, so every setting you change in matrix_rain_coco.asm goes into matrix_rain_coco.c too, and likewise for the CoCo 3 pair.

Staying inside the frame

A frame's work has to finish before the next TV field starts, 60 times a second. That's 14,934 CPU cycles on a CoCo 1/2 and about 29,980 on a CoCo 3, which runs its CPU twice as fast. A frame that runs over makes the rain miss 60 frames a second. The test reports how close each build comes. As shipped, the busiest frame uses 66% of a field on the CoCo 1/2, 83% on the CoCo 3's 80-column build and 46% on its 40-column build.

More drops cost the most. The 80-column CoCo 3 build runs 65 drops because at 70 it runs over a few times a minute, and the test times only 10 frames, which can miss that. After raising NUMDRIPS or adding work to each drop, watch it run for a minute as well.

.\build.ps1 -Run -Composite   # in coco3: a CoCo 3 on a TV, 40 columns

By hand

lwasm builds the programs. --decb asks for Disk BASIC's .bin format, and -D COMPOSITE selects the CoCo 3's 40-column settings. In coco:

lwasm --decb -o matrix_rain_coco.bin matrix_rain_coco.asm

In coco3:

lwasm --decb -o matrix_rain_coco3.bin matrix_rain_coco3.asm
lwasm --decb -D COMPOSITE -o matrix_rain_coco3_cmp.bin matrix_rain_coco3.asm

For the tape and disk images, load the image writers into PowerShell and give them full paths. In coco:

. ..\tools\coco_images.ps1
New-CocoCas -Bin "$PWD\matrix_rain_coco.bin" -Name MATRIX -Path "$PWD\matrix_rain_coco.cas"
New-CocoDsk -Bin "$PWD\matrix_rain_coco.bin" -Name MATRIX -Path "$PWD\matrix_rain_coco.dsk"

With the settings unchanged, each of these commands writes a file identical to the committed one.

Check your change

In coco or coco3:

.\build.ps1 -Test

Each script builds everything, then tests it in XRoar with no window. The CoCo 1/2 test takes about 10 seconds, and the CoCo 3's about 30, since it tests both builds. The CoCo 1/2 test prints:

What each line checks:

Screen RAM
After 400 frames, the CoCo's screen memory matches the reference model's, byte for byte. On the CoCo 3 that includes each cell's colours.
Other RAM
Nothing outside the screen and the program's own memory changed while it ran. This catches a write to the wrong place.
cassette and disk
The tape image loads with CLOADM and runs. So does the disk image with LOADM, when disk11.rom is in the ROM folder; without it the disk check is skipped, which isn't a failure.
Frame cost
The cycles frames 101 to 110 took, against the length of a field. See Staying inside the frame.

If you change tools\coco_images.ps1 or tools\xroar.ps1, run ..\tools\test_coco_tools.ps1 too. It prints PASS, FAIL or SKIP for each of its checks.

Changing the code itself

Anything beyond the settings also goes into the reference model, with the random number calls kept in the same order. The program and its reference model draw every random choice from one generator with the same starting seed. Each call moves the generator on, so one extra or missing call changes every choice after it and the two screens drift apart.

The tests depend on a few things in the .asm files:

  • The labels start, mainloop, waitsync, synced, testdone and progend. The scripts look up their addresses in lwasm's symbol list, to set XRoar's breakpoints and to know where the program sits in memory.
  • The IFDEF TESTFRAMES blocks. The tests assemble extra copies with -D TESTFRAMES=400 and similar, which stop after that many frames and wait at testdone while XRoar saves a snapshot of memory.
  • A program in one piece. Reserve data with FCB or ZMB, not RMB, which leaves a gap and splits the .bin in two. The tape writer refuses a split .bin.

How each screen stores a cell:

CoCo 1/2CoCo 3
Screen$0400–$05FF, 32×16, one byte a cellFrom $2000, 80×24 or 40×24, two bytes a cell: the character, then its colours
Empty cell$80, a graphics block with no pixels litA space, in dark green
CharactersLetters $00–$3F; bit 6 highlights; green blocks $81–$8FColours byte: foreground in bits 5–3, background in bits 2–0

The CoCo 3 tests run on XRoar's CoCo 3 with 512K of memory (-machine coco3 -ram 512).

If something goes wrong

lwasm not found at … Pass -Lwtools <folder holding lwasm.exe>.
Pass -Lwtools, as in Tools. The same goes for XRoar not found and -XRoar.
… cannot be loaded because running scripts is disabled on this system.
Windows is blocking PowerShell scripts. Allow your own scripts once with Set-ExecutionPolicy -Scope CurrentUser RemoteSigned. If you downloaded the repository as a zip, also run Get-ChildItem -Recurse *.ps1 | Unblock-File in its folder.
… differs from the reference model's in … bytes after 400 frames.
The program and its reference model drew different screens. Check that the settings match in both files. The message gives the first place they differ; on the CoCo 3 it names the row, the column and whether the character or its colours differ.
… outside the screen and the program changed while it ran …
The program wrote somewhere it shouldn't. The message gives the first address.
… 400-frame test build never reached testdone. XRoar's log: …
The test copy crashed or got stuck, often because of a setting that stalls it. The log file named in the message shows what XRoar saw.
WARNING: … of 10 frames took longer than a field, so the rain misses 60 fps.
The rain still works but runs slower. See Staying inside the frame.
disk: SKIPPED, no disk11.rom or disk10.rom in …
Not a failure. Put disk11.rom in your ROM folder, or pass -Roms, to test the disk image too.

Every command above was run on Windows 11 on 18 September 2026, with LWTOOLS 4.25, XRoar 1.9 and cc65 2.19, and the output shown is from those runs. With the settings unchanged, every rebuilt file matched the committed one byte for byte. The disk image checks were skipped, because that machine has no disk11.rom. The LWTOOLS steps are the ones that built lwasm there, with Visual Studio 2026.
