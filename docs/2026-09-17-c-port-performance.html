Closing the gap between cc65 and hand-written 6502

The C port of the Matrix rain effect ran at 2.19 times the cost of the assembly it was translated from. Measuring where the cycles went, then reshaping the C around cc65's code generator, brought that to 1.70 without changing a single pixel of output.

Result

Nine changes to the C source, each one measured and each one checked against the assembly's output before the next was attempted.

  • 31,372 Cycles per frame was 40,457, a 22.5% cut
  • 1.70× Of the assembly was 2.19×
  • 2048 / 2048 Screen bytes identical after 400 frames, every step
  • 1,449 B Compiled size was 1,567 B, assembly is 1,000 B

A PET frame at 1 MHz and 60 Hz is 16,667 cycles. Neither version fits in one. The assembly needs 1.11 frames and so runs at roughly 54 fps; the C build now needs 1.88 and runs at roughly 32, up from 25. That the hand-written original also misses 60 fps is worth knowing before anyone chases the last few hundred cycles.

How it was measured

The headline comparison needed the assembly's real number, not an estimate of it.

The assembly baseline

ACME is not installed here and converting the source to a different assembler risked measuring a translation rather than the real thing. Instead the shipped matrix_rain_8032_noclock_v8.prg is copied byte for byte into memory at $0401 inside cc65's 6502 simulator, where its absolute addressing expects to run. Two bytes are then patched: the KERNAL screen clear, because there is no KERNAL in the simulator, and the first byte of the main loop, which becomes an RTS so initialisation returns instead of spinning on a VIA that does not exist. Everything measured after that is the original code, unmodified.

Addresses were read out of the binary rather than assumed, by finding the lda $e840 / and #32 / bne retrace loop and taking the jsr operand that follows it.

Cycle counts

Both versions are built twice, at 100 frames and at 1100, and run under sim65 -c. Subtracting the two totals cancels startup, initialisation and the screen dump, leaving exactly 1000 frames of drawing. Dividing gives the per-frame figure. Frame counts start at 100 rather than 0 because the first frames do less work while drops are still above the screen.

Correctness

The animation is fully deterministic: a fixed LFSR seed and no input. That makes exact comparison possible. Both builds run 400 frames and print all 2048 screen bytes as hex, and the two outputs are compared. They match exactly, and they matched after every single change in the table below. A change that altered the animation would have failed immediately rather than passing as a plausible-looking screenful of rain.

One caveat on the profile numbers. The per-function profile comes from instruction traces of a 2-frame and a 12-frame run, subtracted. Those early frames do less work than the steady state, so the profile totals (36,409 and 28,554) sit below the measured per-frame figures (40,457 and 31,372). The proportions are sound; the absolute values in that table are not the headline numbers.

Every change, and what it bought

Applied in this order. Each figure is the measured drop from the state above it.

Seeds into zero page, and a leaner rnd()

ca65 assembles a constant address below 256 as zero page, so *(unsigned char *)0x00FB costs 3 cycles to touch instead of the 4 an ordinary global costs. The routine runs about 130 times a frame. The same edit dropped a >> 7 that cc65 was expanding into seven shifts.

−3,356Kept

rnd() branches before it overwrites the seed

The old shape saved the seed's top bit into a variable so it could be tested after the shift. cc65 spilled that variable to memory on every call. Testing it first and writing the shift out in both arms of the branch costs a few bytes and removes the spill.

−1,964Kept

Head position as separate low and high byte arrays

cc65 reads an int array by doubling the index, building a pointer and loading through it, which comes to about 44 cycles. Two indexed byte loads cost roughly 12. The assembly kept RAINLO and RAINHI apart for the same reason, and cc65 recognises lo | (hi << 8) and emits the pair of loads.

−1,150Kept

Row offset table split the same way

rowoff[trail] is read once per column per frame, so the same int-array penalty applied here too.

−759Kept

Loop index and current character into zero page

Both are read several times per column. This claims the last two of the eight zero page bytes, $f7 to $fe, which are the same eight the assembly used.

−656Kept

Bounds checks on unsigned wraparound

A negative offset cast to unsigned becomes a very large number, so (unsigned)p < 2048 does the work of checking both ends at once. The tail check cannot use this and still compares signed, because a drop above the screen has a tail far below zero that would read as having fallen off the bottom.

−612Kept

Screen base as a macro rather than a const pointer

static unsigned char *const screen looks like a constant but compiles to a memory load on every access. As a macro the address folds into the instruction.

−564Kept

Screen pointers in zero page

cc65 emits lda ($fd),y directly for a pointer held at a fixed zero page address, instead of copying it into its own scratch pointer first. The read-modify-write that dims the old head compiles to 15 cycles. The setup cost of the pointer nearly cancelled the saving, so this earned almost nothing on its own. It stays because it is what makes the code read like the assembly it came from.

−24Marginal

The draw loop body now costs 17,715 cycles, which is less than the assembly spends on an entire frame including its own random calls. The C loop body is not the problem. What remains is the per-call overhead of the random generator and the helper routines cc65 calls for 16-bit subtraction, neither of which pure C can reach into.

Changes that did not survive

Both were measured and both were reverted. Recording them so they are not tried again.

Four-way branch in rnd()

Branching on the carry bit as well as the tap bit removes the last spilled temporary. It works, and the output stayed identical, but it doubles the length of the function for 0.7%. The C port exists to be read, so this was not a trade worth making. Reinstate it if the last few hundred cycles ever matter more than the source does.

−224Reverted

Hoisting the delay counter into a local

Reading del[col] once instead of three times looked like an obvious win. It made the frame slower. cc65 was already keeping the index in Y across the three accesses, and the extra local cost more than it saved.

+214Reverted

What is left in the gap

12,920 cycles a frame separate the two versions. Here is what they are.

  • The random generator, roughly 2,300 cycles. It compiles to about 54 cycles a call against the assembly's 36, over 130 calls a frame. The remaining overhead is a scratch byte cc65 uses to build (seedlo << 1) | (seedhi & 1), because C has no rotate-through-carry. There is no way to express that operation in C such that cc65 emits ROL.
  • cc65's 16-bit subtraction helpers, roughly 3,000 cycles. Subtracting one variable from another pushes both and calls a runtime routine. It costs about 43 cycles for what the 6502 does inline in 10.
  • The loop body, the balance. Spread thinly across array indexing, comparisons and branching. There is no single hot spot left to attack.

Writing the random generator as an asm() block would recover most of the first item and land somewhere near 28,000 cycles. That is a decision about what the file is for rather than a technical one, and it has not been taken. Matching 18,452 would mean writing the draw loop in assembly too, at which point the C port has stopped being a C port.

Reproducing this

.\build.ps1 -Test
.\tools\profile.ps1

-Test builds the C source for cc65's sim6502 target and prints the screen as text. It then loads the shipped assembly .prg into the same simulator, runs both for 400 frames, and fails unless all 2048 bytes of screen RAM match. Last, it reports the cost of a frame for both versions. The byte-for-byte comparison used throughout this investigation now runs as a regression test on every -Test.

profile.ps1 produces the per-function table above. Its figures for the current code differ from the table's “after” column by a few cycles (draw at 17,722 rather than 17,715) for two reasons. The profiler used during the investigation traced a copy of the source that was laid out three bytes differently from the real build, which moved a few page crossings. The committed one traces a copy that runs to exactly the real build's cycle count, and it refuses to report if the two ever disagree. The old profiler also lumped every local label named @L1 into one row. The committed one charges those cycles to the routines they belong to, which moves about 800 cycles into pushax. Neither change touches a conclusion here: the cc65 helpers still total about 3,100 cycles and the random routines 7,670.
